BioNest: Product Requirements Document and Build Prompt

Version 1.0 · Status: Ready to build

Part 1: PRD

1. Overview

BioNest is a link-in-bio tool. A person claims a username (for example bionest.link/ada) and gets one public page that holds all their links, so they can put a single link in their Instagram, TikTok, X or WhatsApp profile.

It works like Linktree, with a few deliberate improvements aimed at people in Nigeria and across Africa.

2. Problem

  • Social platforms allow only one link in a profile.
  • Linktree solves this but puts its own branding on free pages, gives very little free analytics, and charges in dollars.
  • Creators and small businesses want a page that is clean, fast on weak data, and easy to contact them from (WhatsApp, phone).

3. Goals and non-goals

Goals (v1)

  1. A user can sign up, claim a username, and publish a working page in under 3 minutes.
  2. The public page loads fast on slow mobile data.
  3. Free users get a clean page with no BioNest branding and useful analytics.
  4. All data is real: real accounts, real stored links, real click tracking. No sample or placeholder data in the product.

Non-goals (v1)

  • Selling products, courses or taking payments from visitors
  • Social media scheduling or auto-reply
  • Team accounts
  • Native mobile apps (the web app must work well on phones)

4. Target users

User Need
Creators (musicians, comedians, influencers) One link for all their content
Small business owners (salons, caterers, tailors) A contact page with WhatsApp and phone buttons
Freelancers and professionals A simple online presence without a website

5. What makes BioNest different (the "slight changes")

# Change Why
1 No BioNest branding on free pages Common complaint about the market leader
2 Useful free analytics: clicks by day, country, referrer, device Free analytics elsewhere are close to a single total
3 Built-in WhatsApp and phone buttons The main way people are contacted locally
4 Link scheduling (show and hide links on dates) Promotions that end automatically
5 Very light public page Works on weak 3G
6 Naira pricing for the paid plan (phase 2) Dollar pricing is expensive locally

6. Functional requirements

6.1 Accounts

  • Sign up and log in with email and password, and with Google.
  • Email verification required before a page can be published.
  • Password reset by email.
  • Users can delete their account, which deletes all their data.

6.2 Username and page URL

  • Username: 3 to 30 characters, lowercase letters, numbers, underscore and hyphen. Must start with a letter or number.
  • Must be unique. Availability is checked live while typing.
  • Reserved names are blocked (for example: admin, login, signup, dashboard, api, help, support, settings, pricing, about, terms, privacy, app, www, bionest).
  • Public page lives at /{username}.

6.3 Profile

  • Display name (up to 50 characters), bio (up to 160 characters).
  • Profile photo upload (JPG, PNG or WebP, max 2 MB). The app resizes and compresses it on upload.

6.4 Links

  • Add, edit, delete, enable or disable, and drag-to-reorder links.
  • Link types:
    • Standard link: title and URL. URL must start with https:// or http://. Other schemes (such as javascript:) are rejected.
    • WhatsApp: phone number in international format, optional pre-filled message. Opens https://wa.me/{number}?text={message}.
    • Phone: opens tel:.
    • Email: opens mailto:.
    • Header: a text divider, not clickable.
  • Optional per-link schedule: show_from and show_until date and time (stored in UTC, shown in the user's timezone).
  • No hard limit on the number of links.

6.5 Social icons

  • A row of icons under the bio. Supported: Instagram, TikTok, X, YouTube, Facebook, LinkedIn, Snapchat, Telegram, Spotify, GitHub, Website.
  • User enters a handle or URL for each, and the app builds the correct link.

6.6 Appearance

  • At least 8 built-in themes (background, button style, font, colors).
  • Custom option: background color or gradient, button color, text color, button shape (square, rounded, pill), font choice from a short list.
  • Live preview of the page while editing, shown in a phone frame next to the editor.

6.7 Sharing

  • Copy page link button.
  • QR code generated for the page URL, downloadable as PNG and SVG.

6.8 Analytics (all real, recorded from actual visits)

  • Recorded events: page view and link click.
  • Per event store: timestamp, link id (for clicks), country, referrer source, device type, and a daily-rotating anonymous visitor hash.
  • Dashboard shows, for a selectable range (7 days, 30 days, 90 days):
    • Total views, total clicks, click-through rate
    • Daily chart of views and clicks
    • Top links by clicks
    • Countries
    • Referrers (Instagram, TikTok, WhatsApp, X, Facebook, YouTube, Direct, Other)
    • Devices (mobile, desktop, tablet)
  • Bots and link-preview crawlers are filtered out.
  • No IP addresses are stored.

6.9 Public page

  • Server-rendered so it loads quickly and works without heavy JavaScript.
  • Proper title, description and social share image (Open Graph) per page.
  • Page respects the schedule on links.
  • Shows "Page not found" for unknown usernames.
  • Small "Report this page" link for abuse.

6.10 Plans

  • Plan field exists on every account from day one: free or pro.
  • v1 launch: everything above is available on Free. Pro is introduced in phase 2 (see roadmap).

7. Data model

Table Key fields
profiles id (matches auth user), username (unique), display_name, bio, avatar_url, theme (JSON), plan, created_at
links id, profile_id, type, title, url, whatsapp_number, message, position, is_active, show_from, show_until, created_at
social_links id, profile_id, platform, url, position
events id, profile_id, link_id (nullable), type (view or click), country, referrer, device, visitor_hash, created_at
reports id, profile_id, reason, details, created_at

Security rule: users can read and change only their own rows. Public visitors can read only active profile and link data through the public page. Only the server can write to events.

9. Non-functional requirements

  • Speed: public page under 100 KB of data transferred, loads in under 2 seconds on a slow 3G connection, Lighthouse performance score of 90 or higher on mobile.
  • Security: row-level security on all tables, URL validation on every link, rate limits on sign up, login, username checks and report submissions.
  • Privacy: no IP storage, no third-party ad trackers. Follow the Nigeria Data Protection Act. Provide a privacy notice and data deletion.
  • Accessibility: keyboard navigable, readable color contrast, alt text on images.
  • Reliability: click redirect must still work even if event recording fails.

10. Roadmap

Phase Scope
Phase 1 (MVP) Everything in section 6 except paid plans
Phase 2 Pro plan billed in naira (Paystack), custom domains, extra themes, CSV export of analytics
Phase 3 Email collection block, link thumbnails, UTM builder, link shortener

11. Success metrics

  • Time from sign up to a published page: median under 3 minutes
  • Share of sign-ups who publish a page: 60% or higher
  • Weekly active page owners, and number of page views per page
  • Mobile Lighthouse performance score: 90 or higher

12. Risks and open questions

Part 2: Build prompt

Copy everything inside the box below into your AI coding tool (for example Claude Code, Cursor or Lovable).

You are a senior full-stack engineer. Build BioNest, a production-ready link-in-bio web app (similar to Linktree). This is a REAL build: no mock data, no seeded demo users, no hardcoded sample links, no fake analytics. Every screen must read and write real data in a real database. Empty states (for example "You have no links yet") are shown when there is no data.

## Tech stack
- Next.js (App Router) with TypeScript and Tailwind CSS
- Supabase for Postgres, Auth (email/password and Google), and Storage (avatars)
- Row Level Security enabled on every table
- Deploy target: Vercel
- Libraries: dnd-kit (drag to reorder), zod (validation), qrcode (QR generation), recharts (analytics charts)
- All secrets via environment variables. Provide a `.env.example`. Never commit secrets.

## What to build

### 1. Auth
- Sign up, log in, log out, password reset, Google sign-in.
- Require verified email before a page can be published.
- Protect /dashboard/* routes. Redirect logged-out users to /login.
- Account deletion in settings that deletes the user's profile, links, events and avatar file.

### 2. Onboarding
- After first login, send the user to /onboarding: choose username (live availability check, debounced), display name, optional photo, add first link.
- Username rules: 3-30 chars, lowercase letters, numbers, underscore, hyphen; must start with a letter or number; unique; block reserved words: admin, login, signup, dashboard, api, help, support, settings, pricing, about, terms, privacy, app, www, bionest, go, onboarding, reset-password.

### 3. Dashboard (/dashboard)
- Left: links editor. Right: live phone-frame preview of the public page that updates as the user edits.
- Link types: standard (https/http URL only; reject javascript:, data:, etc.), whatsapp (international number + optional prefilled message, builds https://wa.me/NUMBER?text=...), phone (tel:), email (mailto:), header (non-clickable divider text).
- Add, edit, delete, enable/disable, drag-to-reorder (persist position).
- Optional schedule per link: show_from and show_until (store UTC, display in user's timezone). Public page hides links outside their window.
- Social icons row: Instagram, TikTok, X, YouTube, Facebook, LinkedIn, Snapchat, Telegram, Spotify, GitHub, Website. User enters a handle or URL; build the correct URL.
- Profile: display name (max 50), bio (max 160), avatar upload (JPG/PNG/WebP, max 2 MB, resize and compress client-side or server-side before storing).
- Copy-link button and QR code (download PNG and SVG).

### 4. Appearance (/dashboard/appearance)
- At least 8 built-in themes plus custom controls: background color or gradient, button color, text color, button shape (square, rounded, pill), font from a short list (use next/font, self-hosted, no external font requests at runtime).
- Store theme as JSON on the profile. Preview updates live.

### 5. Public page (/{username})
- Server-rendered, minimal JavaScript, under 100 KB transferred, mobile-first. Target Lighthouse mobile performance 90+.
- No BioNest branding on any page (free plan included). Only a small "Report this page" link.
- Per-page metadata: title, description, Open Graph image (use avatar or generate one).
- Unknown username shows a proper 404.
- Each link button points to /go/{linkId}.
- Record a "view" event on each page load (server-side, no client tracker script).

### 6. Click tracking (/go/{linkId})
- Route handler that looks up the link, records a "click" event, then returns a 302 redirect to the destination (or the wa.me / tel: / mailto: URL).
- Redirect MUST still happen even if recording the event fails.
- Respect schedule and is_active: if the link is not live, return 404.

### 7. Analytics (/dashboard/analytics)
- Range selector: 7, 30, 90 days.
- Show: total views, total clicks, click-through rate, daily chart (views and clicks), top links, countries, referrers, devices.
- Data comes only from the real `events` table, aggregated with SQL (use Postgres functions or views for performance).
- Event fields: profile_id, link_id (nullable), type, country, referrer, device, visitor_hash, created_at.
- Country: read from the hosting provider's geo header (on Vercel: x-vercel-ip-country).
- Referrer: map the Referer header to Instagram, TikTok, WhatsApp, X, Facebook, YouTube, Direct, Other. Note that in-app browsers often hide the referrer; mark those as Direct.
- Device: parse the User-Agent into mobile, tablet, desktop.
- Visitor hash: SHA-256 of (IP + User-Agent + daily rotating salt + profile_id). Never store the raw IP.
- Filter out bots, crawlers and link-preview fetchers (WhatsApp, Facebook, Twitter, Slack, Telegram previews, Googlebot, etc.).
- Only the server (service role) may insert events. Users can only read events for their own profile.

### 7b. Report abuse
- /report form (or modal) saving to a `reports` table. Rate limited.

### 8. Settings (/dashboard/settings)
- Change display name, change username (re-validate, keep it unique), change email/password, delete account.

### 9. Landing page (/)
- Simple, fast marketing page: headline, short explanation, sign up button, three feature highlights (clean free pages, real analytics, WhatsApp buttons). Plus /terms and /privacy pages with clear placeholder legal text marked for lawyer review.

## Database schema (Supabase SQL migration)
Create tables with these columns (use uuid primary keys, timestamptz for times):
- profiles: id (references auth.users), username (unique, citext or lower-case check), display_name, bio, avatar_url, theme jsonb, plan text default 'free', disabled boolean default false, created_at
- links: id, profile_id, type (standard|whatsapp|phone|email|header), title, url, whatsapp_number, message, position int, is_active boolean default true, show_from timestamptz null, show_until timestamptz null, created_at
- social_links: id, profile_id, platform, url, position
- events: id, profile_id, link_id null, type (view|click), country, referrer, device, visitor_hash, created_at (index on profile_id, created_at)
- reports: id, profile_id, reason, details, created_at

RLS policies:
- profiles/links/social_links: owner can select, insert, update, delete their own rows. Public read of only non-disabled profiles and active, currently-scheduled links for the public page (via server queries or a public view).
- events: no client insert. Owners can select their own profile's events.
- reports: anyone can insert (rate limited at the API level); only service role can read.
- Storage bucket `avatars`: public read, authenticated users can write only inside their own folder.

## Quality requirements
- Validate all input with zod on both client and server. Sanitize all output.
- Rate limit: sign up, login, username check, report submission, click route (basic per-IP limit).
- Accessible: keyboard navigation, color contrast, alt text, focus states.
- Responsive: dashboard works on phones.
- Friendly error messages, loading states, and empty states everywhere.
- Include automated tests for: username validation, URL validation, schedule logic, referrer mapping, bot filtering.
- Write a README with: setup steps, env variables, how to run the Supabase migration, how to deploy to Vercel.
